## 4. E2E (Chrome for Testing, 모의 사이트)

`tests/e2e/extension.e2e.test.ts` 흐름:

1. 빌드한 `dist/`를 로드합니다.
2. 페이지와 서비스 워커의 `https://*` 요청을 CDP Fetch로 가로채 합성 응답을 줍니다(`tests/e2e/mock-sites.ts`). 실제 서비스에는 접속하지 않습니다.

4. 실제로 저장된 파일을 다운로드 폴더에서 읽어 검사합니다.

### 실제 데이터에서 찾아 고친 것

1. **ChatGPT 추론 모델의 `commentary` 채널** — 표본 대화에서 16개가 있었습니다. 화면에 표시된 텍스트와 대조해 보니 하나도 보이지 않았습니다(접힌 사고 패널 안에 있음). 그래서 thinking으로 분류해 문서에서 빼고 JSON·ZIP에 남깁니다.
2. **ChatGPT `container.exec` 코드 실행과 그 출력** — 화면에 보이지 않습니다. 그래서 건너뛰고, 건너뛴 사실을 검증 결과에 표시합니다. 예전 Code Interpreter(`python`)는 그대로 보입니다.
3. **ChatGPT·Claude의 DOM 대체 경로** — 새 선택자로 바꿨습니다. 가상화된 목록은 스크롤하면서 `data-chatgpt-search-unit-key` / `data-turn-key`로 중복 없이 모읍니다. 사용자 메시지 줄바꿈(`white-space: pre-wrap`)이 사라지던 버그도 고쳤습니다.
4. **도구를 많이 쓰는 Claude 대화** — 도구 결과 86개(웹 페이지 본문, 명령 로그)가 문서를 뒤덮었습니다. 2,000자를 넘는 도구 출력은 문서에 앞부분만 넣고 전체는 JSON·ZIP에 남기도록 바꾸고, 검증 결과에 표시합니다.
5. 화면의 사용자 메시지 수는 가상화 때문에 일부만 보입니다. 그래서 하한값으로만 비교합니다(화면 수가 추출 수보다 많을 때만 경고).

### 6.1 v1.1: 사용자 피드백으로 확인하고 고친 것

### 6.2 v1.2: 실제 대화로 압축 알고리즘 비교

사용자 요청("실제 내 채팅 세션 여러 개로 어떤 압축 알고리즘이 좋은지 테스트")에 따라, 로그인된 Chrome에서 최근 ChatGPT 대화 300개의 길이를 읽기 전용으로 조사했습니다. 본문 2만 자 이상인 긴 대화 30개를 받았습니다(현재 분기만 남기고 제목·사고 과정·숨은 도구 출력·검색 결과 본문은 제거, 약 41 MB). 다운로드 전에 파일 이름·출처·크기를 알리고 사용자 허락을 받았습니다. 파일은 저장소 밖 임시 폴더에서 로컬로만 처리했고, 실험이 끝난 뒤 삭제했습니다. 저장소에는 집계 수치만 있습니다.

- 짧은 시간에 대화 300여 개를 읽자 ChatGPT가 `429`(요청 과다)를 돌려주었습니다. 요청을 멈췄다가 15–60초 간격으로 천천히 다시 받았습니다. 확장은 한 번에 대화 하나만 읽으므로 실제 사용에는 해당하지 않습니다.
- 결과와 방법은 [압축 실험 보고서](compression-lab.md)에 있습니다. 요약하면, 손실의 가장 큰 원인은 v1.1이 아주 긴 메시지의 가운데를 잘라 버린 것이었습니다(대화 27개 중 메시지 1–3개짜리가 여러 개, 최대 18만 토큰). v1.2는 그 부분도 커버리지 선택 후보로 넣고, 원문·코드 몫을 줄였습니다.
- 이 실험에서 바뀐 것: 기본 선택 방식(관련도 → 커버리지), 예산 배치(코드 25% → 10%, 최근 메시지 상한 6,000/4,000 → 2,500/1,500토큰), 잘린 메시지의 가운데를 "중요한 맥락"으로 발췌, 예산이 남으면 한 번 더 채우기, 최근 원문과 겹치는 코드·마지막 요청 인용 줄이기, 같은 메시지 발췌의 원래 순서 유지.

### 6.3 v1.2.1: 최신 방법·모델과 2차 비교

사용자 요청으로 새로 받은 실제 대화 31개(ChatGPT 28개 + Claude.ai 3개, 약 173만 토큰)로 2차 비교를 했습니다. 다운로드마다 사용자 허락을 받았고, 로컬에서만 처리한 뒤 삭제했습니다. 이번에는 ChatGPT를 20초 간격으로 받아 요청 과다 제한이 두 번만 걸렸습니다(각 2분 대기).

- "앞 문장 잃은 문장" 지표를 새로 만들었습니다. v1.2.0 엔진은 이런 문장이 50%였고, v1.2.1은 앞 문장과 묶어 고르면서 32%가 되었습니다(종합 점수 동일, 59.0).

### 6.5 v1.3.2: 사용자 보고 — "화면의 사용자 메시지(5개)가 추출된 수(2개)보다 많습니다"

- **증상**: 사용자 메시지 2개짜리 ChatGPT 대화로 인수인계를 만들자 위 경고가 떴습니다. 문서에는 메시지 4개가 모두 들어 있었습니다.
- **원인**: chatgpt.com은 앱 안에서 다른 대화로 옮겨 가도 이전 대화를 지우지 않고 `display: none` 상자 안에 남겨 둡니다. 실제 계정에서 다른 대화에 갔다가 돌아오자 페이지 안의 사용자 말풍선이 7개, 보이는 것은 2개였습니다. 화면 메시지 수가 숨은 말풍선까지 세어서 경고가 잘못 나왔습니다. API가 실패할 때 쓰는 DOM 대체 수집도 같은 선택자를 써서, 그 경우에는 이전 대화의 메시지가 문서에 섞일 수 있었습니다.
- **수정**: 네 사이트 모두 화면 메시지 수와 DOM 대체 수집에서 실제로 렌더링된 요소(`checkVisibility()`)만 씁니다. 스크롤해서 화면 밖에 있는 메시지는 그대로 셉니다. 같은 구조의 합성 화면을 테스트로 넣었고, 수정 전 코드에서는 이 테스트가 정확히 "5"로 실패합니다.
- **같은 문서에서 찾은 것**: "파일 · 경로"에 정부 사이트 주소(`*.go.kr`)의 앞부분이 Go 파일(`*.go`)처럼 들어갔습니다. 확장자 뒤에 `.kr`처럼 점과 글자가 이어지면 파일로 보지 않게 했습니다. 첨부 사진은 서명된 ChatGPT 링크(`…&sig=…`)로 들어갔습니다. 다른 AI는 이 링크를 열 수 없으므로 인수인계 문서에는 `[이미지: 파일 이름]`만 남깁니다. 코드 블록 안은 바꾸지 않고, 내보내기(MD·DOCX 등)는 그대로입니다.

### 6.6 v1.3.3: 실제 계정 전체 흐름 — 인수인계본 대 전체 추출본

- **방법**
  - ChatGPT 대화 448개 중 30개를 2025-12부터 기간 전체에서 고르게 뽑았습니다. 17개가 프로젝트 안 대화입니다. Claude는 37개 중 10개와 프로젝트 대화 1개를 뽑았고, 그중 2개는 메시지가 없는 빈 대화였습니다.

## 7. 검증하지 못한 것

- Gemini·Grok 실제 계정에서 확장의 전체 흐름. ChatGPT·Claude는 §6.6에서 답변 아래 패널로 확인했고, 사용자 요청에 따라 두 서비스만 했습니다.
- 실제 계정의 툴바 팝업: 자동화 도구가 확장 페이지를 열 수 없어 모의 사이트 E2E로만 확인했습니다.
- "답변 생성 중" 상태는 실제로 한 번 만났지만(§6.6), 새 경고는 합성 테스트로만 확인했습니다. 메시지를 보내지 않기로 해서 새 대화의 첫 답변도 실제로 재현하지 않았습니다.
- 실제 대화의 PDF·DOCX·HWPX·ZIP: §6.6에서는 인수인계와 JSON만 만들었습니다.
- v1.3.4는 수집 코드를 바꾸지 않아서, 다시 만든 추출본을 서버 기록과 다시 대조하지는 않았습니다(§6.6에서 39/39 일치).
- Chrome을 다시 띄운 직후 첫 작업에서 패널 회전 아이콘이 한 번 다시 만들어진 원인은 찾지 못했습니다(§6.7, 재현되지 않음).
- 대화 기록에 텍스트가 없는 첨부(PDF, 이미지, ChatGPT에 올린 파일)의 내용은 인수인계에 넣을 수 없습니다. 이름만 적고 다시 첨부를 요청하라고 안내합니다. 첨부 몫(예산의 12%)은 실험이 아니라 판단으로 정했습니다. 합성 대화에는 첨부가 없어 압축 실험과 질의응답 평가로는 이 값을 비교하지 못했습니다.
- 실제 데이터에서 Gemini 여러 페이지 수집 — 계정에 10턴이 넘는 대화가 없었습니다. 모의 데이터로는 확인했습니다.
- 실제 Claude·Grok·Gemini의 이미지·첨부 다운로드 — ChatGPT 이미지만 실제로 확인했습니다.
- 실제 대화의 수식·표 렌더링 품질(합성 fixture로만 확인)
- 한컴오피스(한글)로 HWPX 열기, Microsoft Word로 DOCX 열기
- Windows, Chrome 155 이외 버전(최소 116으로 선언했지만 실행 확인은 155와 CI의 최신 stable만), Edge 등 다른 Chromium 브라우저. Linux는 CI의 E2E(모의 사이트)로만 확인했습니다.
- 인쇄 창에서 사용자가 “PDF로 저장”을 누르는 마지막 단계. E2E는 같은 인쇄 페이지를 `page.pdf`로 출력해 확인했습니다.
- 메모리 사용량은 Node 힙 증가량(1M: 44 MB)만 측정했습니다. 확장 프로세스의 메모리는 측정하지 않았습니다.
- 압축 실험의 1·2차 지표는 단어·개체·문장의 보존을 재는 근사치입니다. 3차 실험의 질의응답 평가는 합성 대화의 사실 질문만 쟀습니다. 실제 대화로는 질의응답 평가를 하지 않았고, 다음 AI가 인수인계 문서로 실제 작업(코드 수정, 판단)을 얼마나 잘 이어 가는지는 재지 않았습니다. 실험 데이터는 한 사용자의 ChatGPT 대화(1차 27개, 2차 28개)와 Claude.ai 대화 3개뿐이고, Gemini·Grok 대화로는 실험하지 않았습니다. 모델 방식(EmbeddingGemma 2, LLMLingua-2)은 기기 부하 때문에 전체 데이터로 끝까지 비교하지 못했습니다.

1. 저장소 **밖에** 빈 폴더를 만듭니다.
2. 실제로 쓰듯이(사이드바로 대화를 옮겨 다니며) 대화마다 답변 아래 Lucian 패널에서 **인수인계**와 **JSON** 내보내기를 만들고, 두 파일을 그 폴더로 옮깁니다. 파일 이름은 바꿀 필요가 없습니다(문서 안 원본 링크로 짝을 맞춥니다).
3. `npm run check:real -- <폴더>`를 실행합니다. 메시지 수, 구조, 예산, 캐시 없이 다시 계산한 결과와의 일치, 발췌·원문 줄·링크가 원래 대화에 그대로 있는지, 깨진 파일 목록 항목, 보존율을 집계합니다. 대화별 상세는 그 폴더의 `report.txt`에 남습니다(대화를 인용하므로 커밋하지 마세요).
4. 끝나면 폴더를 지웁니다.

### 실제 계정에서 직접 확인하기 (권장)

1. `npm run build`를 실행하고, `chrome://extensions`에서 개발자 모드를 켠 뒤 `dist/`를 로드합니다.
2. 각 서비스에서 짧은 대화 하나와 긴 대화 하나를 열고 **새로고침**합니다.
3. 답변 아래 Lucian 버튼이 보이는지 확인하고, 인수인계 → 첫 줄 안내문, 요청 흐름, 결정, 현재 상태가 맞는지 확인합니다. 파일 이름이 `대화-제목-lucian-handoff-날짜.md`인지도 봅니다.
4. PDF·Markdown·Word를 차례로 내보내고 검증 결과를 열어 경고를 확인합니다. 경고가 사실과 다르면 이슈로 알려 주세요.
5. 다른 형식(HWPX·ZIP)을 내보내고, 한글에서 열리는지와 ZIP의 `verification-report.md`를 확인합니다.
