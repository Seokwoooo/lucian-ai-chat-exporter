## 3. 단위 테스트 (135개)

- **어댑터 (13개)**: URL에서 대화 ID 추출(ChatGPT 프로젝트·GPT 경로, Gemini `/u/1`·Gem 경로 포함). 4개 서비스의 파서를 합성 fixture로 검사합니다.

## 4. E2E (Chrome for Testing, 모의 사이트)

`tests/e2e/extension.e2e.test.ts` 흐름:

1. 빌드한 `dist/`를 로드합니다.
2. 페이지와 서비스 워커의 `https://*` 요청을 CDP Fetch로 가로채 합성 응답을 줍니다(`tests/e2e/mock-sites.ts`). 실제 서비스에는 접속하지 않습니다.
3. 팝업 버튼과 답변 아래 Lucian 버튼을 클릭합니다.
4. 실제로 저장된 파일을 다운로드 폴더에서 읽어 검사합니다.
5. v1.3.3: 4개 사이트 모두 페이지에 숨겨진 이전 대화(`display: none`)를 넣고 인수인계를 만듭니다. 이어서 API가 500을 돌려주게 해서 화면 읽기로도 만듭니다. 잘못된 "화면 메시지가 더 많다" 경고가 없고 이전 대화가 문서에 섞이지 않아야 통과합니다. 수정 전 코드로 돌리면 사용자가 본 것과 같은 "화면 5개, 추출 2개" 경고로 실패하는 것을 확인했습니다.
6. v1.3.4: 1M 토큰 테스트에서 처리 중 회전 아이콘이 작업 하나에 몇 번 만들어지는지 셉니다. 팝업(인수인계, MD·HTML·DOCX·HWPX)과 답변 아래 패널은 1번, 답변 아래 버튼 아이콘은 2번(처리 중으로, 다시 원래대로) 이하여야 통과합니다. 수정 전 코드로는 팝업에서 6번으로 실패합니다.
7. v1.3.6: 4개 사이트 모두 이미지가 있는 대화를 Markdown으로 내보내면 팝업에 선택지 3개가 뜨는지 확인하고, 세 가지를 모두 실행합니다. ZIP은 풀어서 `.md`의 모든 이미지 링크가 실제 파일을 가리키는지, 폴더 방식은 다운로드 폴더에서 `.md`의 링크가 모두 실제 파일인지와 `images.folder` 검사가 통과하는지, 넣지 않기는 서비스 링크가 하나도 없는지 봅니다. ChatGPT는 답변 아래 패널에서도 같은 선택지가 뜨고 고른 대로 ZIP이 저장되는지 확인합니다.

| 사이트 | 인수인계 | MD | DOCX | HWPX | HTML | TXT | JSON | ZIP | PDF(인쇄 페이지) |
|---|---|---|---|---|---|---|---|---|---|
| ChatGPT | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ 원본 첨부 `spec.pdf` 포함 | ✅ |
| Claude | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ⚠️ 경고(의도된 결과: 첨부 원본에 접근 불가 → 추출 텍스트만) | ✅ |
| Gemini | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Grok | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

각 칸에서 확인한 것:

- 작업 단계가 `done`(PDF는 `print`)입니다.
- 검증 결과에 `fail`이 없습니다.
- 원본 메시지 수와 일치합니다.
- 다운로드가 완료되었고, 저장된 파일 크기가 생성 크기와 같습니다.
- DOCX/HWPX/ZIP은 압축이 풀립니다.
- JSON의 메시지 수가 일치합니다.
- 이미지가 문서에 포함되었습니다(`1/1`).
- 인수인계 파일 이름은 `<대화 제목>-lucian-handoff-YYYY-MM-DD.md` 형식이고(v1.3.5부터 제목이 앞에 붙음, E2E가 작업의 제목으로 기대 이름을 만들어 비교), `## 0. 기본 정보`와 `[#m1]`을 포함합니다.

그 밖의 E2E 확인:

- 지원하지 않는 페이지에서 안내가 표시되고 버튼이 비활성화됩니다.
- **답변 아래 Lucian 버튼 (4개 사이트)**: 답변 도구 막대마다 버튼이 하나씩 생기고(ChatGPT 2, Claude 1, Gemini 1, Grok 1), 사용자 메시지 도구 막대에는 생기지 않습니다. 버튼 → 패널 → 인수인계 실행 → `lucian-handoff-YYYY-MM-DD.md` 저장 → 패널에 ✓ “인수인계 파일 저장 완료” 표시, “세부 정보”는 눌러야 펼쳐짐(v1.3.8) → Esc로 닫힘. Claude에서 사이트가 도구 막대 버튼을 지우면 Lucian 버튼도 함께 사라집니다.
- **다운로드 이름 충돌**: `onDeterminingFilename`으로 모든 다운로드 이름을 다시 지정하는 테스트용 “다운로드 관리” 확장을 함께 설치했습니다. 수정 전 빌드로는 사용자가 겪은 것과 같은 `b273b523-….md`(blob UUID) 이름으로 저장되는 것을 재현했고, 수정 후에는 모든 형식이 원래 이름으로 저장됩니다.
- 다크 모드와 라이트 모드 화면을 캡처했습니다(`docs/images`).
- PDF는 인쇄 페이지를 Chrome 인쇄 엔진(`page.pdf`, Skia/PDF m155)으로 출력한 뒤 `pdftotext`로 한글 제목과 본문이 추출되는지 확인했습니다.

E2E로 찾아 고친 버그:

- offscreen 문서에서 `chrome.runtime.getManifest`를 쓸 수 없어 **모든 내보내기 형식이 실패**하던 문제
- 인수인계 참조 색인에 thinking 첫 줄이 나오던 문제
- ZIP 검증 문구에서 첨부 개수가 바이트(“0 B/1개”)로 표시되던 문제
- (v1.1) 패널 상태를 갱신할 때마다 전체를 다시 그려 키보드 포커스가 사라지고 Esc가 먹지 않던 문제
- (v1.1) 섹션 번호를 내용에 따라 매기도록 바꾼 뒤, 인수인계 구조 검증이 예전 섹션 제목을 찾아 **실패로 표시**하던 문제. 사이트별 인수인계 E2E도 이제 내보내기처럼 `fail` 검사가 하나도 없어야 통과합니다.

### 실제 데이터에서 찾아 고친 것

1. **ChatGPT 추론 모델의 `commentary` 채널** — 표본 대화에서 16개가 있었습니다. 화면에 표시된 텍스트와 대조해 보니 하나도 보이지 않았습니다(접힌 사고 패널 안에 있음). 그래서 thinking으로 분류해 문서에서 빼고 JSON·ZIP에 남깁니다.
2. **ChatGPT `container.exec` 코드 실행과 그 출력** — 화면에 보이지 않습니다. 그래서 건너뛰고, 건너뛴 사실을 검증 결과에 표시합니다. 예전 Code Interpreter(`python`)는 그대로 보입니다.
3. **ChatGPT·Claude의 DOM 대체 경로** — 새 선택자로 바꿨습니다. 가상화된 목록은 스크롤하면서 `data-chatgpt-search-unit-key` / `data-turn-key`로 중복 없이 모읍니다. 사용자 메시지 줄바꿈(`white-space: pre-wrap`)이 사라지던 버그도 고쳤습니다.
4. **도구를 많이 쓰는 Claude 대화** — 도구 결과 86개(웹 페이지 본문, 명령 로그)가 문서를 뒤덮었습니다. 2,000자를 넘는 도구 출력은 문서에 앞부분만 넣고 전체는 JSON·ZIP에 남기도록 바꾸고, 검증 결과에 표시합니다.
5. 화면의 사용자 메시지 수는 가상화 때문에 일부만 보입니다. 그래서 하한값으로만 비교합니다(화면 수가 추출 수보다 많을 때만 경고).

### 6.2 v1.2: 실제 대화로 압축 알고리즘 비교

사용자 요청("실제 내 채팅 세션 여러 개로 어떤 압축 알고리즘이 좋은지 테스트")에 따라, 로그인된 Chrome에서 최근 ChatGPT 대화 300개의 길이를 읽기 전용으로 조사했습니다. 본문 2만 자 이상인 긴 대화 30개를 받았습니다(현재 분기만 남기고 제목·사고 과정·숨은 도구 출력·검색 결과 본문은 제거, 약 41 MB). 다운로드 전에 파일 이름·출처·크기를 알리고 사용자 허락을 받았습니다. 파일은 저장소 밖 임시 폴더에서 로컬로만 처리했고, 실험이 끝난 뒤 삭제했습니다. 저장소에는 집계 수치만 있습니다.

- 짧은 시간에 대화 300여 개를 읽자 ChatGPT가 `429`(요청 과다)를 돌려주었습니다. 요청을 멈췄다가 15–60초 간격으로 천천히 다시 받았습니다. 확장은 한 번에 대화 하나만 읽으므로 실제 사용에는 해당하지 않습니다.
- 결과와 방법은 [압축 실험 보고서](compression-lab.md)에 있습니다. 요약하면, 손실의 가장 큰 원인은 v1.1이 아주 긴 메시지의 가운데를 잘라 버린 것이었습니다(대화 27개 중 메시지 1–3개짜리가 여러 개, 최대 18만 토큰). v1.2는 그 부분도 커버리지 선택 후보로 넣고, 원문·코드 몫을 줄였습니다.
- 이 실험에서 바뀐 것: 기본 선택 방식(관련도 → 커버리지), 예산 배치(코드 25% → 10%, 최근 메시지 상한 6,000/4,000 → 2,500/1,500토큰), 잘린 메시지의 가운데를 "중요한 맥락"으로 발췌, 예산이 남으면 한 번 더 채우기, 최근 원문과 겹치는 코드·마지막 요청 인용 줄이기, 같은 메시지 발췌의 원래 순서 유지.

### 6.3 v1.2.1: 최신 방법·모델과 2차 비교

사용자 요청으로 새로 받은 실제 대화 31개(ChatGPT 28개 + Claude.ai 3개, 약 173만 토큰)로 2차 비교를 했습니다. 다운로드마다 사용자 허락을 받았고, 로컬에서만 처리한 뒤 삭제했습니다. 이번에는 ChatGPT를 20초 간격으로 받아 요청 과다 제한이 두 번만 걸렸습니다(각 2분 대기).

- 모델 없는 알고리즘 9개(KL-Sum, SumBasic, centroid, LSA, facility location, Lin–Bilmes submodular, 정보량 순위, CliffCompaction 채팅판, 참조 복원)를 추가했습니다. 커버리지보다 같은 분량에서 확실히 나은 것은 없었습니다.
- "앞 문장 잃은 문장" 지표를 새로 만들었습니다. v1.2.0 엔진은 이런 문장이 50%였고, v1.2.1은 앞 문장과 묶어 고르면서 32%가 되었습니다(종합 점수 동일, 59.0).
- 실험 중 잘린 메시지에서 보이는 문장을 잘못 판단하던 버그를 찾아 고쳤습니다.
- EmbeddingGemma 2와 LLMLingua-2는 실행 환경을 만들어 일부만 돌렸습니다. 임베딩 계산이 맥북을 눈에 띄게 느리게 해서(사용자 보고) 대화 3개에서 중단했습니다. 측정한 속도(초당 약 45문장)로는 확장 안에서 쓸 수 없다고 판단했습니다. LLMLingua-2는 한국어 문장을 깨뜨려서 제외했습니다. 자세한 내용은 [압축 실험](compression-lab.md)의 2차 실험 절에 있습니다.

### 6.4 v1.3: 질의응답 평가와 실제 대화 확인

- **질의응답 평가 (합성 대화)**: 인수인계 문서만 본 AI가 원래 대화에 대한 질문에 맞게 답하는지 쟀습니다. 정답이 정해진 사실 17개를 심은 합성 대화 10개를 썼고, 읽는 AI는 Claude Haiku 5.5입니다. 문서마다 새 세션을 열었고 도구, 설정, 메모리는 없었습니다. 호출은 약 430회, 비용은 약 $2.3입니다.

### 6.5 v1.3.2: 사용자 보고 — "화면의 사용자 메시지(5개)가 추출된 수(2개)보다 많습니다"

- **증상**: 사용자 메시지 2개짜리 ChatGPT 대화로 인수인계를 만들자 위 경고가 떴습니다. 문서에는 메시지 4개가 모두 들어 있었습니다.
- **원인**: chatgpt.com은 앱 안에서 다른 대화로 옮겨 가도 이전 대화를 지우지 않고 `display: none` 상자 안에 남겨 둡니다. 실제 계정에서 다른 대화에 갔다가 돌아오자 페이지 안의 사용자 말풍선이 7개, 보이는 것은 2개였습니다. 화면 메시지 수가 숨은 말풍선까지 세어서 경고가 잘못 나왔습니다. API가 실패할 때 쓰는 DOM 대체 수집도 같은 선택자를 써서, 그 경우에는 이전 대화의 메시지가 문서에 섞일 수 있었습니다.
- **수정**: 네 사이트 모두 화면 메시지 수와 DOM 대체 수집에서 실제로 렌더링된 요소(`checkVisibility()`)만 씁니다. 스크롤해서 화면 밖에 있는 메시지는 그대로 셉니다. 같은 구조의 합성 화면을 테스트로 넣었고, 수정 전 코드에서는 이 테스트가 정확히 "5"로 실패합니다.
- **같은 문서에서 찾은 것**: "파일 · 경로"에 정부 사이트 주소(`*.go.kr`)의 앞부분이 Go 파일(`*.go`)처럼 들어갔습니다. 확장자 뒤에 `.kr`처럼 점과 글자가 이어지면 파일로 보지 않게 했습니다. 첨부 사진은 서명된 ChatGPT 링크(`…&sig=…`)로 들어갔습니다. 다른 AI는 이 링크를 열 수 없으므로 인수인계 문서에는 `[이미지: 파일 이름]`만 남깁니다. 코드 블록 안은 바꾸지 않고, 내보내기(MD·DOCX 등)는 그대로입니다.

### 6.9 v1.3.6: 사용자 질문 — PDF에 이미지가 들어가는가, Markdown의 이미지는 어떻게 하는가

- **PDF**: 이미지를 미리 내려받아 인쇄 페이지에 넣습니다. 인쇄 직전에 이미지가 제대로 그려졌는지 확인하고, 못 받거나 깨진 이미지는 "이미지 N/M개를 가져오지 못했습니다" 경고로 남깁니다.
  - 실제 대화로 PDF를 만들면 인쇄 창이 떠서 자동으로 확인할 수 없습니다. 그래서 PDF와 같은 이미지 수집·같은 렌더러를 쓰는 HTML로 확인했습니다. PDF 자체는 E2E에서 같은 인쇄 페이지를 PDF로 출력해 확인합니다(§4).
  - 이미지가 있는 실제 대화 5개(ChatGPT 4개: 이미지 24·12·8·4장, Claude 1개: 2장)를 답변 아래 패널로 HTML로 내보냈습니다. 받은 파일을 열어 보니 49장이 실제 이미지(PNG·JPEG·WebP 헤더 확인)로 들어 있었습니다.
  - 나머지 1장은 ChatGPT 서버가 다운로드를 거부(403)한 도구 단계의 이미지였고, 패널에 경고로 표시됐습니다. ChatGPT 화면에서도 보이지 않는 이미지로 보이지만, 확실하지는 않습니다.
- **Markdown**: 이미지가 서비스 주소 링크로만 남았습니다. 확인해 보니 이 주소는 로그인한 브라우저에서만 열립니다. ChatGPT(`estuary/content`, 서명 포함)와 Claude(`files/…/preview`) 모두 쿠키 없이 열면 403이었습니다(페이지 안에서 응답 상태만 확인). 그래서 Obsidian·VS Code 같은 다른 프로그램에서는 이미지가 보이지 않습니다. 그런데도 패널에는 경고 없이 "완료"로만 나왔습니다(검증 결과에 정보 한 줄만 있었음).
  - 수정: 이미지가 있는 대화를 Markdown으로 내보내면 "Markdown 파일에는 이미지가 들어가지 않습니다"라는 안내와 함께 세 가지 중에서 고르게 합니다(사용자가 정한 선택지). ZIP으로 묶기, `.md` 옆에 `제목_files` 폴더로 저장, 이미지는 넣지 않기입니다. 팝업과 답변 아래 패널 모두에서 고를 수 있습니다.
  - 넣지 않기를 고르면, 쓸 수 없는 링크 대신 `[이미지: 설명]`을 남깁니다. 이미지가 없는 대화는 이전처럼 바로 `.md`로 저장됩니다.
  - 실제 사이트에서 이 선택지를 다시 확인하지는 않았습니다(§7).

### 6.13 v1.3.8: Grok 인수인계마다 "메시지 1개 변환 실패" — 원인과 수정

- **재현**: 사용자가 로그인해 둔 Chrome에서 §6.11에서 사용자가 알려 준 grok.com 대화를 찾아, 확장과 같은 요청(`response-node`, `load-responses`)으로 받은 실제 응답에 v1.3.7 파서를 그대로 돌렸습니다(파서만 묶어 페이지에서 실행, 대화 내용은 꺼내지 않음). 메시지 16개는 모두 정상인데 원본 메시지를 17개로 세고 1개를 "빠짐"으로 기록했습니다. 사용자가 본 결과와 같습니다.
- **원인**: 첫 질문의 `parentResponseId`가 `response-node` 목록에 없는 ID를 가리킵니다. 그 ID를 `load-responses`로 직접 받아 보니 내용이 빈 `sender: "system"` 응답이었습니다(화면에는 나오지 않음). 파서가 경로를 거슬러 올라가며 이 ID까지 메시지로 세고, 받아 온 응답에 없으니 "빠짐"이 됐습니다. 계정의 최근 Grok 대화 60개가 **모두** 이 구조여서, v1.3.7에서는 Grok 대화를 내보낼 때마다 같은 오류가 났습니다. 모의 데이터의 첫 질문에는 부모가 없어 E2E로는 잡지 못했습니다.
- **수정**: 경로는 `response-node`에 있는 노드만 따라가고(분기 경로도 같음), `system` 응답은 메시지로 세지 않습니다. Grok fixture의 첫 질문도 실제처럼 숨은 system 응답을 부모로 갖게 바꿨습니다.
- **두 번째로 찾은 것**: 같은 60개를 돌려 보니 한 대화의 AI 답변 3개가 아직 "빠짐"이었습니다. 세 답변 모두 Grok이 "This model is temporarily unavailable. Please try a different model." 오류로 생성에 실패한 응답이었습니다. 본문은 없고 `streamErrors`만 있으며, grok.com 화면은 이 자리에 오류 상자를 보여 줍니다. 문서도 화면처럼 이 자리에 `> **Grok error:** …` 한 줄을 남기도록 했습니다.
- **결과 (실제 대화 60개)**: 빠진 메시지 63개(60개 대화 모두) → **0개**. 원본 메시지 373개 = 문서 메시지 373개입니다. 경로 수정만 했을 때 메시지 370개는 내용까지 수정 전과 같았고(다른 분기 수 1개도 같음), 여기에 오류 답변 3개가 오류 문구로 더해졌습니다. 단위 테스트 2개를 추가했고 E2E는 10 / 10 통과입니다.

### 6.14 v1.3.8: 사용자 보고 — Gemini에서 L 버튼이 오른쪽 끝에 붙음

- **원인**: 실제 gemini.google.com 도구 막대(2026-10-21 확인)는 [좋아요, 싫어요, 복사, 더보기] 뒤에 남은 폭을 모두 차지하는 `.spacer`가 있습니다. 버튼을 막대 끝에 붙이다 보니 그 빈 칸 뒤, 즉 오른쪽 끝에 놓였습니다. 다른 사이트에는 이런 빈 칸이 없습니다.
- **수정**: 어댑터가 버튼을 넣을 자리를 정할 수 있게 `actionAnchor()`를 두고, Gemini는 `.spacer` 앞을 돌려줍니다. 사이트의 버튼은 옮기거나 바꾸지 않습니다. 빈 칸이 없으면 이전처럼 끝에 붙입니다.
- **확인**: 실제 Gemini 페이지의 두 답변 모두 같은 구조임을 확인하고, 버튼을 그 자리로 옮겨 "더보기(⋯)" 바로 오른쪽에 붙는 것을 화면으로 확인했습니다. E2E의 모의 Gemini 막대에도 `.spacer`를 넣어, 버튼이 복사 버튼 바로 뒤·빈 칸 앞에 들어가는지 검사합니다.

### 6.15 v1.3.8: 사용자 보고 — 압축 추출(인수인계)이 전체 추출보다 토큰이 많음

사용자가 같은 대화를 전체 Markdown 추출과 인수인계로 각각 받았더니, 인수인계 쪽이 더 컸습니다. ChatGPT 4개 메시지 대화(약 2천 토큰)는 전체 추출의 129%, Grok 10개 메시지 대화는 138%였습니다(o200k 132%·134%). 두 파일은 저장소 밖에서만 다뤘고, 테스트에는 같은 모양의 합성 대화만 넣었습니다.

- **원인**: 원문이 1만 2천 토큰 이하면 "짧은 대화"로 보고 원문 전체를 넣었습니다. 그 위에 읽는 AI용 안내문(5개 항목), 기본 정보 표, 요청 흐름·현재 상태·미완료·링크 같은 색인 섹션을 더 붙였습니다(v1.3.4 `fullIndex`). 그래서 1만 2천 토큰 이하 대화의 인수인계는 **항상** 전체 추출보다 컸습니다.
- **전수 조사**: 같은 문제가 다른 경로로도 생기는지 보려고, 대화 모양 18가지(짧은 Q&A, 긴 붙여넣기, 긴 도구 출력, 첨부, 이미지만, 검색 링크, 짧은 메시지 수백 개, 생각만 있는 답변, 코드 등) × 크기 최대 15단계(60–15만 토큰), 고정 예제 5개(인사 한 번, 질문만 등), 실제 파일 2개, 모두 263개를 돌렸습니다. 전체 추출 6가지(Markdown 한·영 × 이미지 링크 유무, TXT 한·영)와 비교했고, 토큰은 엔진 추정치·o200k·cl100k로 셌습니다. **263개 중 177개**가 전체 추출보다 작지 않았습니다. 찾은 경로는 다섯 가지입니다.
  1. 1만 2천 토큰 이하 대화: 원문 전체 + 안내문 + 색인 섹션(대부분)
  2. 압축 모드인데 긴 도구 출력이 있는 대화: 원문 분량은 도구 출력 전체로 셌는데, 전체 추출은 도구 출력을 2천 자로 줄입니다. 예산이 전체 추출보다 커질 수 있었습니다(105%).
  3. 메시지가 아주 많고 짧은 대화(이미지만, "네" 수백 개): 원문 분량에 메시지 머리줄이 빠져, 전체 추출이 3만 토큰인데 "짧은 대화"로 처리됐습니다.
  4. 작은 예산에서도 고정 최소치(최근 원문 400, 코드 300, 첨부 400, 마지막 메시지 400토큰 등)가 그대로였습니다.
  5. 반복 줄 안내(`_(… 1줄 생략 …)_`)가 지운 줄보다 길었습니다. 사용자의 Gemini 인수인계에서는 이 안내가 **표 머리글 줄을 지워** 표가 깨져 있었습니다.
  - 토큰 추정 자체도 문제였습니다. 이전 규칙("한글 1자 1토큰, 나머지 4자 1토큰")은 o200k 대비 `[#m12]` 참조를 0.52배, 표를 0.46배, 이모지를 0.33배로 셌습니다. 인수인계에는 이런 마크업이 많아서, 엔진이 2/3로 계산해도 실제로는 전체와 거의 같을 수 있었습니다(영어 시나리오: 추정 70%, o200k 99%).
- **고친 것**
  - **크기 보장**: 원문 분량(`sourceTokens`)을 전체 Markdown 추출 크기로 바꿨습니다(`fullExportTokens`). 예산은 그 12%(8k–32k)이되 **2/3를 넘지 않습니다**(`handoffBudget`). 예산 맞춤 단계 뒤에도 넘으면 선택 섹션을 빼고(`squeeze`) 최근 원문을 더 줄이고, 그래도 넘으면 아래 핵심 문장 형식으로 만듭니다. 이 형식은 문장을 빼서 항상 상한 안에 듭니다.
  - **짧은 대화는 핵심 문장 형식**: 예산이 4천 토큰 미만(전체 추출 약 6천 토큰 미만)이면 섹션 대신, 대화 원문에서 핵심 문장만 메시지 순서대로 남기고 생략한 곳은 `…`로 표시합니다. 마지막 메시지·마지막 요청·첫 요청의 앞부분과 사용자 문장을 먼저 넣고, 나머지는 섹션의 "중요한 맥락"과 같은 개념 커버리지로 고릅니다. 예산이 아주 작으면 꼬리말 → 출처 줄 → 긴 안내문 순으로 줄입니다. 경계(4천)는 아래 보존율 비교로 정했습니다.
  - **작은 예산**: 최소치들을 예산에 비례해 줄였습니다(8천 토큰 이상은 그대로). 최근 원문을 고를 때 메시지 머리줄 비용(16토큰)을 셉니다.
  - **토큰 추정**: BPE 토크나이저처럼 단어·숫자 묶음·문장부호·줄바꿈 단위로 나눠 세는 방식으로 바꿨습니다. 가중치는 실제 파일·합성 대화·코드·문서 42개로 o200k에 맞췄고, 맞추는 데 쓰지 않은 문서 10개에서 0.93–1.01배입니다.
  - **반복 줄 안내**: 표의 줄은 지우지 않고, 안내가 지운 줄보다 길면 줄을 그대로 둡니다.
  - **안내문**: 문서에 있는 섹션만 가리킵니다(결정·지시가 없으면 그 항목을 빼고, ⚠️ 항목이 없으면 그 항목을 뺍니다).
  - **언어**: 첫 번째 파일(한국어 대화)의 인수인계가 영어였습니다. 사용자의 두 번째 메시지가 긴 영어 화면 붙여넣기여서, 사용자 글 전체의 한글 비율이 20% 아래로 떨어졌기 때문입니다. 이제 사용자 메시지별로 보고, 3분의 1 이상이 한국어면 한국어로 만듭니다.
  - **굵은 글씨**: 문장을 나눌 때 `**네. 별도입니다!**`가 `**네.`와 `별도입니다!** …`로 갈라져, 짝 없는 `**`가 뒤 문서를 굵게 만들 수 있었습니다. 짝 없는 `**` 하나를 뺍니다.
- **결과**
  - 같은 263개 중 전체 추출보다 작지 않은 경우 **0개**. 인수인계/전체 추출 비율은 o200k로 중앙값 43%, 최대 72%입니다.
  - 사용자의 두 파일(원문 Markdown에서 대화를 다시 읽어 계산): 129% → **66%**, 138% → **67%**(o200k 65%·67%). 둘 다 핵심 문장 형식이고 한국어입니다. `npm run check:real`(같은 방식으로 만든 JSON + 인수인계)도 예산 초과 0, 전체 추출보다 작지 않음 0, 원문 줄 99/99가 그 메시지에 있음입니다. 사용자의 예전 인수인계 2개를 같은 검사에 넣으면 2/2가 "전체 추출보다 작지 않음"(최대 135%)으로 잡힙니다.
  - 보존율(압축 실험 지표, 실제 짧은 대화 3개 — 위 두 개와 사용자의 다른 Gemini 인수인계에 들어 있던 원문): 같은 크기(전체 추출의 2/3)의 섹션 형식 59.5·64.8·81.3 → 핵심 문장 형식 **87.5·88.0·85.3**, 같은 크기의 단순 커버리지는 86.1·85.3·73.1입니다.
  - 긴 대화(섹션 형식)는 그대로입니다. 질의응답 평가 대화 20개를 같은 자료로 이전 엔진과 비교하면, 정답이 문서에 있는 비율은 짧은 메시지형 96.5% → 98.2%, 긴 답변형 100% → 100%, 종합 점수는 92.9 → 92.4, 93.5 → 93.1, 문서는 3–6% 짧습니다(이전 엔진은 마크업을 적게 세어 실제로는 예산을 넘었습니다).
  - 회귀 테스트(`tests/handoff/size.test.ts`, `tests/shared/tokens.test.ts`), E2E(4개 사이트에서 인수인계가 같은 대화의 Markdown·TXT 내보내기의 70%보다 작음), 확장의 검증 보고서에 "인수인계가 전체 추출보다 작지 않음" 경고(`handoff.size`)를 넣었습니다. 검사용 실제 토크나이저 `gpt-tokenizer`는 개발 의존성으로만 씁니다(4.0.0 고정, 확장에는 들어가지 않음).
- **함께 발견했지만 고치지 않은 것**: 첫 번째 파일의 ChatGPT 답변에서 "다음 명령어를 입력하세요." 뒤에 와야 할 명령어가 전체 추출과 인수인계 **양쪽 모두에서** 빠져 있습니다. 인수인계가 아니라 수집 단계의 문제입니다. 코드로는 두 가지 원인이 가능합니다. 하나는 명령어를 속성에 담은 컴포넌트(`<CodeBlock code="…"/>`)이고, 다른 하나는 숨은 표시 문자 안의 위젯입니다. 실제 서버 기록을 보지 못해 고치지 않았습니다. 같은 조사에서 찾은 다른 결함 하나는 고쳤습니다. 위치가 맞지 않는 `sources_footnote` 참조(`matched_text: " "`)가 답변의 첫 공백을 지워 `## 3.`이 `##3.`이 되던 문제입니다(기존 fixture의 `# 조사 결과`로 확인).

## 7. 검증하지 못한 것

- v1.3.8 인수인계 크기 수정은 사용자의 파일 2개(원문 Markdown에서 대화를 다시 읽음)와 합성 대화로만 확인했습니다. 실제 계정에서 고친 확장으로 여러 대화를 다시 만들어 `npm run check:real`을 돌리지는 않았습니다(브라우저 확장 연결 불가). 실제 토크나이저 비교는 OpenAI의 o200k·cl100k만 했습니다. Claude·Gemini의 토크나이저는 공개되어 있지 않습니다.
- 위 ChatGPT 답변에서 명령어(코드 블록)가 빠진 원인(§6.15)

- v1.3.8 Grok 수정은 실제 데이터에 파서를 직접 돌려 확인했습니다(§6.13). 실제 계정에서 확장 프로그램을 설치한 채 버튼을 눌러 보는 전체 흐름은 다시 하지 않았습니다(사용 중인 Chrome에 개발 빌드를 올리지 않음). Gemini 버튼 위치도 실제 페이지에서 같은 자리로 옮겨 보기만 했습니다.

- Gemini·Grok 실제 계정에서 확장의 전체 흐름. ChatGPT·Claude는 §6.6에서 답변 아래 패널로 확인했고, 사용자 요청에 따라 두 서비스만 했습니다.
- 실제 계정의 툴바 팝업: 자동화 도구가 확장 페이지를 열 수 없어 모의 사이트 E2E로만 확인했습니다.
- "답변 생성 중" 상태는 실제로 한 번 만났지만(§6.6), 새 경고는 합성 테스트로만 확인했습니다. 메시지를 보내지 않기로 해서 새 대화의 첫 답변도 실제로 재현하지 않았습니다.
- 실제 대화의 PDF·DOCX·HWPX·ZIP: §6.6에서는 인수인계와 JSON만 만들었습니다.
- v1.3.4는 수집 코드를 바꾸지 않아서, 다시 만든 추출본을 서버 기록과 다시 대조하지는 않았습니다(§6.6에서 39/39 일치).
- Chrome을 다시 띄운 직후 첫 작업에서 패널 회전 아이콘이 한 번 다시 만들어진 원인은 찾지 못했습니다(§6.7, 재현되지 않음).
- v1.3.6의 Markdown 이미지 선택지는 모의 사이트 E2E(4개 사이트, 세 방식 모두)로만 확인했습니다. 실제 계정에서 확장으로 다시 확인하려면 Chrome을 다시 시작해야 해서, 사용자가 쓰는 중인 브라우저를 끄지 않고 남겨 두었습니다. 실제 PDF도 인쇄 창 때문에 HTML로 대신 확인했습니다(§6.9).
- 대화 기록에 텍스트가 없는 첨부(PDF, 이미지, ChatGPT에 올린 파일)의 내용은 인수인계에 넣을 수 없습니다. 이름만 적고 다시 첨부를 요청하라고 안내합니다. 첨부 몫(예산의 12%)은 실험이 아니라 판단으로 정했습니다. 합성 대화에는 첨부가 없어 압축 실험과 질의응답 평가로는 이 값을 비교하지 못했습니다.
- 실제 데이터에서 Gemini 여러 페이지 수집 — 계정에 10턴이 넘는 대화가 없었습니다. 모의 데이터로는 확인했습니다.
- 실제 Claude·Grok·Gemini의 이미지·첨부 다운로드 — ChatGPT 이미지만 실제로 확인했습니다.
- 실제 대화의 수식·표 렌더링 품질(합성 fixture로만 확인)
- 한컴오피스(한글)로 HWPX 열기, Microsoft Word로 DOCX 열기
- Windows, Chrome 155 이외 버전(최소 116으로 선언했지만 실행 확인은 155와 CI의 최신 stable만), Edge 등 다른 Chromium 브라우저. Linux는 CI의 E2E(모의 사이트)로만 확인했습니다.
- 인쇄 창에서 사용자가 “PDF로 저장”을 누르는 마지막 단계. E2E는 같은 인쇄 페이지를 `page.pdf`로 출력해 확인했습니다.
- 메모리 사용량은 Node 힙 증가량(1M: 44 MB)만 측정했습니다. 확장 프로세스의 메모리는 측정하지 않았습니다.
- 압축 실험의 1·2차 지표는 단어·개체·문장의 보존을 재는 근사치입니다. 3차 실험의 질의응답 평가는 합성 대화의 사실 질문만 쟀습니다. 실제 대화로는 질의응답 평가를 하지 않았고, 다음 AI가 인수인계 문서로 실제 작업(코드 수정, 판단)을 얼마나 잘 이어 가는지는 재지 않았습니다. 실험 데이터는 한 사용자의 ChatGPT 대화(1차 27개, 2차 28개)와 Claude.ai 대화 3개뿐이고, Gemini·Grok 대화로는 실험하지 않았습니다. 모델 방식(EmbeddingGemma 2, LLMLingua-2)은 기기 부하 때문에 전체 데이터로 끝까지 비교하지 못했습니다.

## 8. 재현 방법

```bash
npm ci
npm run check                # typecheck + lint + 단위 테스트 + 빌드
npm run e2e:install-chrome   # 최초 1회
npm run test:e2e             # 결과 파일: test-output/e2e/, 1M 성능: bench-results/e2e-chrome-1m.json
npm run bench                # bench-results/handoff-node.json
```

### 실제 대화로 인수인계본과 전체 추출본 비교하기 (`npm run check:real`)

1. 저장소 **밖에** 빈 폴더를 만듭니다.
2. 실제로 쓰듯이(사이드바로 대화를 옮겨 다니며) 대화마다 답변 아래 Lucian 패널에서 **인수인계**와 **JSON** 내보내기를 만들고, 두 파일을 그 폴더로 옮깁니다. 파일 이름은 바꿀 필요가 없습니다(문서 안 원본 링크로 짝을 맞춥니다).
3. `npm run check:real -- <폴더>`를 실행합니다. 메시지 수, 구조, 예산, 캐시 없이 다시 계산한 결과와의 일치, 발췌·원문 줄·링크가 원래 대화에 그대로 있는지, 깨진 파일 목록 항목, 보존율을 집계합니다. 대화별 상세는 그 폴더의 `report.txt`에 남습니다(대화를 인용하므로 커밋하지 마세요).
4. 끝나면 폴더를 지웁니다.

### 실제 계정에서 직접 확인하기 (권장)

1. `npm run build`를 실행하고, `chrome://extensions`에서 개발자 모드를 켠 뒤 `dist/`를 로드합니다.
2. 각 서비스에서 짧은 대화 하나와 긴 대화 하나를 열고 **새로고침**합니다.
3. 답변 아래 Lucian 버튼이 보이는지 확인하고, 인수인계 → 첫 줄 안내문, 요청 흐름, 결정, 현재 상태가 맞는지 확인합니다. 파일 이름이 `대화-제목-lucian-handoff-날짜.md`인지도 봅니다.
4. PDF·Markdown·Word를 차례로 내보내고 검증 결과를 열어 경고를 확인합니다. 경고가 사실과 다르면 이슈로 알려 주세요.
5. 다른 형식(HWPX·ZIP)을 내보내고, 한글에서 열리는지와 ZIP의 `verification-report.md`를 확인합니다.
