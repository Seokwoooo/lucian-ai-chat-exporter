작성일 2026-10-17 (2차 실험, 3차 실험 추가) · 코드 `scripts/compression-lab/`

> **v1.3**: 3차 실험(질의응답 평가)에서 v1.2.1의 문서가 예산의 대부분을 구조 섹션에 쓰고 있음을 찾았습니다. 그래서 분량 배분과 결정 규칙을 다시 정했습니다. 기본 예산 정답률은 78.8% → 97.6%입니다(합성 대화). 실제 대화 31개에서는 개선 폭이 작았습니다(종합 60.1 → 60.9, 사실 보존 29.7% → 33.2%, 출력 −7%). 아래 [3차 실험](#3차-실험-질의응답-평가-v13)을 먼저 보세요. 1·2차 실험 결과는 기록으로 남깁니다.

인수인계 문서는 긴 대화를 원문의 약 12%(8k–32k 토큰)로 줄입니다. 같은 분량에서 어떤 알고리즘이 정보를 가장 많이 남기는지 **사용자의 실제 ChatGPT 대화**로 비교했습니다. 모든 후보는 LLM·임베딩·외부 API를 쓰지 않습니다. 원문 단위(문장, 목록 항목, 코드 블록, 표)를 그대로 고르는 추출 방식이라 없던 내용을 만들지 않습니다.

1. **가장 큰 손실 원인은 알고리즘이 아니라 긴 메시지였습니다.** 실제 대화는 메시지 수가 적고(중앙값 10개) 메시지 하나가 아주 긴 경우가 많았습니다(메시지 1–3개에 17만–18만 토큰인 대화도 있음). v1.1은 마지막 메시지들을 앞뒤만 남기고 잘라서 그 가운데가 통째로 사라졌습니다. v1.2는 잘린 가운데의 문장·표·목록도 다른 과거 문장과 같은 조건으로 선택 후보에 넣습니다.
2. **선택 방식은 예산 제약 최대 커버리지가 가장 좋았습니다.** 모든 예산에서 TF-IDF, TextRank, MMR, 앞부분(lead), 최근 원문보다 사실·핵심어·개체를 더 많이 남겼습니다. v1.2는 과거 맥락을 이 방식으로 고르고, 결정·요청·최근 원문 등 이미 문서에 있는 개념은 덮인 것으로 칩니다. 모든 개념이 덮이면 남은 예산은 관련도 순으로 채웁니다.
3. **원문 최근 부분과 코드의 몫을 줄였습니다.** 마지막 두 메시지는 각 2,500토큰, 그 앞은 1,500토큰까지만 원문으로 넣고, 코드 몫은 25% → 10%로 줄였습니다. 최근 원문에 이미 있는 코드는 코드 섹션에서 다시 넣지 않습니다. 마지막 메시지 상한을 3,500·4,000토큰으로 올리면 '최근' 점수는 2–4점 오르지만 종합 점수는 0.8–0.9점 내려갑니다.
4. **구조화 섹션은 유지했습니다.** 순수 커버리지가 같은 분량에서 점수가 더 높지만, 결정·제약·요청 흐름·현재 상태처럼 다음 AI가 바로 써야 하는 정보에 이름을 붙여 주지 못하고 사용자 단어 재현율도 낮습니다(65% 대 76%). 그 차이(종합 약 4점)는 구조의 비용으로 받아들였습니다.
5. **무손실 축약으로 줄일 수 있는 양은 작습니다.** 정확한 중복 2.1%, 이전 버전 코드까지 3.4%, 거의 같은 문장까지 6.2%(대화별 중앙값 2.4%, 최대 13.7%)입니다. 실제 대화는 반복이 적어서, 원문의 12%로 줄이면서 손실이 없을 수는 없습니다. 기본 예산에서 핵심어는 88%, 사실 문장은 29%가 남고, 예산을 원문의 50%로 늘리면 사실 문장 59%, 핵심어 96%가 남습니다.
6. **채택하지 않은 것**: 군더더기 단어 제거(`coverage+compact`)는 모든 예산에서 2–4점 더 높지만 원문 문장을 바꾸므로 "원문 그대로 발췌" 원칙에 맞지 않습니다. 중복 제거를 먼저 하는 조합(`dedupe+…`)은 효과가 없었습니다(±0.5점).

## 2차 실험: 최신 방법과 모델 비교 (v1.2.1)

사용자 요청으로 2025–2026년에 나온 방법과 오픈 모델까지 넓혀 다시 비교했습니다. 데이터는 새로 받은 실제 대화 **31개**입니다(ChatGPT 28개 + Claude.ai 3개, 원문 약 173만 토큰). 첫 실험처럼 로컬에서만 처리했고, 끝난 뒤 삭제했습니다.

### 추가한 알고리즘 (모두 모델 없음)

| 이름 | 출처·방법 |
|---|---|
| `klsum` | KL-Sum (Haghighi & Vanderwende 2009): 요약의 단어 분포를 원문 분포에 가깝게 |
| `sumbasic` | SumBasic (Nenkova & Vanderwende 2005): 자주 나온 단어 우선, 쓴 단어는 확률을 제곱해 낮춤 |

| `facility` | Facility location: 원문의 모든 문장마다 비슷한 문장이 요약에 하나는 있도록 (TF-IDF 유사도) |
| `submodular` | Lin & Bilmes (2011): facility location + 주제 다양성 보상 |
| `surprisal` | Selective Context(2023)의 아이디어를 GPT-2 대신 대화 자체의 단어·단어쌍 확률로: 정보량(놀라움)이 큰 문장 우선 |
| `cliff` | CliffCompaction(2026)을 채팅에 맞게: 첫 요청과 최근 K개 메시지는 그대로, 예전 사용자 메시지도 그대로, 예전 답변은 앞 N글자만. 고쳐 쓰지 않고 자르기만 함 |
| `coverage+facility` | 개념 커버리지 + facility location (둘 다 submodular라 합도 submodular) |
| `…+repair` | 참조 복원("Referential Dangling", 2026): "이 방식은…", "그래서…", "This…"로 시작하는 문장은 앞 문장과 한 묶음으로 고름 |

새 지표 **dangl**(낮을수록 좋음)도 추가했습니다. 남긴 문장 중 앞 문장을 가리키는 표현("이", "그래서", "따라서", "This", "So"…)으로 시작하는데 그 앞 문장이 출력에 없는 비율입니다. 그런 문장은 다음 AI가 무엇을 가리키는지 알 수 없습니다. 2026년 논문에서는 이런 문장의 앞 문장을 되살리면 질의응답 정확도가 29–34점 올랐습니다.

### 알게 된 것

1. **고전 요약 알고리즘 중 새로 나은 것은 없었습니다.** 2009년 KL-Sum과 facility location은 사실 문장 보존에서 가장 높았지만(43%), 최근 상황과 사용자 단어를 크게 놓쳤습니다. 개념 커버리지와 합친 `coverage+facility`도 커버리지와 같은 수준이었습니다(61.3 대 61.2). 복잡도를 늘릴 이유가 없어 엔진에는 넣지 않았습니다. KL-Sum은 대화 하나에 약 5초가 걸려 너무 느립니다.
2. **에이전트용 최신 방법(CliffCompaction)은 채팅에는 맞지 않았습니다.** 도구 출력이 대부분인 코딩 에이전트 세션을 위한 방법이라, 답변 본문이 정보의 대부분인 채팅에서는 54.9점이었습니다.
3. **커버리지 선택의 숨은 문제는 '앞 문장 잃은 문장'이었습니다.** 커버리지·facility·KL-Sum은 고른 "그래서…" 문장의 절반 이상에서 앞 문장을 버렸습니다. v1.2.1은 그런 문장을 앞 문장과 묶어 비용을 합쳐 고릅니다. 종합 점수는 그대로(59.0)이면서 dangl이 49.8% → 31.8%가 되었습니다. 남은 경우는 대부분 한 줄짜리 목록 항목(완료·미완료·실패)이고, 대화당 평균 1개 남짓입니다. "중요한 맥락" 발췌만 보면 14%입니다.
4. **실험하다 찾은 버그도 고쳤습니다.** 잘린 메시지에서 어떤 문장이 보이는지를 내용만으로 찾아서, 같은 문장이 앞부분에 한 번 나오면 가운데의 같은 문장도 "보인다"고 판단했습니다. 이제는 메시지 안에서 순서대로 찾습니다.

### 모델 방식 (EmbeddingGemma 2, LLMLingua-2)

- **EmbeddingGemma 2** (Google, 2026-10, 텍스트 270M, Apache 2.0): 한국어 같은 뜻 문장 유사도 0.94, 한국어–영어 0.91, 관계없는 문장 0.75로 품질은 좋았습니다. 하지만 M2 Pro GPU에서 실제 대화 문장을 **초당 약 45개**(짧은 합성 문장은 94개)밖에 처리하지 못했습니다. 1M 토큰 대화(약 2.5만 문장)는 약 9분이 걸리고, 계산하는 동안 맥북이 눈에 띄게 느려졌습니다. 그래서 대화 3개까지만 계산하고 중단했습니다. 브라우저 확장 안(WebGPU)에서는 이보다 느릴 가능성이 높아서, "10초 안에 인수인계" 요구를 지킬 수 없습니다. 제품 후보에서 뺐습니다.
- **LLMLingua-2** (Microsoft, xlm-roberta-large 토큰 분류): 토큰을 지우는 방식이라 원문 문장이 바뀝니다. 영어 회의록으로 학습한 모델이라 한국어 문장은 조사·동사가 빠졌습니다(합성 예: "실패하면 세 번까지 다시 시도한 뒤 … 보냅니다" → "실패하면 세 보냅니다"). 파일 경로도 잘렸습니다(`rollback0.sh` → `rollback0.`). 원문 그대로 발췌한다는 원칙과 한국어 품질 두 가지 모두 맞지 않아 대규모 실험 전에 제외했습니다.
- 결론: 이 제품에는 **모델 없는 개념 커버리지 + 참조 복원**이 가장 맞습니다. 모델은 품질 이득이 불확실한데 비용(용량 수백 MB, 처리 시간 수 분, 기기 부하)은 확실합니다.

## 3차 실험: 질의응답 평가 (v1.3)

1·2차 실험의 지표는 단어·개체·사실 문장이 몇 % 남았는지 재는 간접 지표였습니다. 3차 실험에서는 목적을 직접 쟀습니다. **인수인계 문서만 받은 AI가 원래 대화에 대한 질문에 맞게 답하는가**입니다. 그리고 문서 크기를 바꿔 가며 "토큰 대비 질"을 비교했습니다.

### 방법

- **대화**: 합성 대화 10개입니다(한국어 5, 영어 5, 각 3만·5만·8만·13만·22만 토큰). 결제 서비스를 만드는 프로젝트 대화이고, 대화마다 정답이 정해진 사실 **17개**를 곳곳에 심었습니다.
  - 초반: 프로젝트 목표, 금지한 라이브러리, 커밋 규칙, 응답 시간 제약
  - 결정: 나중에 바뀐 DB와 바꾼 이유
  - 중반: 앞 문장을 가리키는 문장("이 방식은 … 헤더로 보내야 합니다"), 파일 경로, 배포 실패 원인, 명령어, 재시도 횟수, 거절된 제안
  - 후반: 완료·미완료 작업, 긴 설계 문서 한가운데의 토큰 만료 시간, 다음 작업
  - 대화에 답이 없는 질문 2개(출시일, 클라우드 리전)도 넣었습니다.
- **채우는 내용**: 기술 대화 문장 템플릿 약 40개(언어별)를 조합했습니다. 일부러 헷갈리는 값도 섞었습니다. 다른 기능의 재시도 횟수와 세션 시간, 측정된 p95, 다른 파일 경로 같은 것들입니다.
- **대화 모양 두 가지**: 짧은 메시지 수백 개(기본)와, 1차 실험의 실제 대화처럼 메시지 6–12개에 답변 하나가 수천~수만 토큰인 모양(`QA_SHAPE=long`)입니다.
- **읽는 AI**: 방법마다 같은 예산으로 문서를 만들었습니다. 그 문서만 본 Claude Haiku 5.5가 질문에 답했습니다. 문서마다 새 세션을 열었고 도구, 설정, 플러그인, 메모리는 없었습니다. 문서로 알 수 없으면 "모름"이라고 답하게 했습니다.
- **채점**: 정규식 정답표로 채점했고, "틀림"으로 나온 답은 모두 직접 읽어 확인했습니다. 한국어 "예"와 "Yes, rejected"를 정답으로 인정하도록 정답표를 고쳤습니다.
- **빠른 대리 지표**: 정답 문장이 문서에 그대로 들어 있는 비율(`presence`)도 쟀습니다. 정답이 문서에 있으면 Haiku는 92–100% 맞혔고, 방법 사이의 순위도 정답률과 같았습니다. 설정 조정은 이 지표로 몇 초 만에 하고, 결과는 Haiku로 다시 확인했습니다.
- **비용**: Haiku 호출 약 430회, 약 $2.3입니다. 맥북에서는 모델을 돌리지 않았습니다.

| 방법 | 정답률 | 답이 없는 질문에 지어냄 | 평균 크기 |
|---|---|---|---|
| coverage (제품과 같은 토큰 수) | **97.4%** | 0% | 13,094토큰 |
| coverage | 96.5% | 0% | 11,331토큰 |
| 전체 대화 그대로 (1회) | 95.3% | 0% | 107,351토큰 |
| skeletonCoverage | 90.6% | 0% | 11,368토큰 |
| **Lucian v1.2.1** | **78.8%** | 0% | 15,539토큰 |
| Lucian v1.1 | 53.8% | 0% | 15,832토큰 |
| 마지막 부분만 (`recent`) | 10.3% | 0% | 12,195토큰 |

- 같은 질문끼리 짝지어 비교하면 v1.2.1만 맞힌 경우가 9번, coverage만 맞힌 경우가 69번이었습니다. 1회차와 2회차의 차이는 1–2점입니다.
- **전체 대화를 그대로 줘도 최선이 아니었습니다.** 13만·22만 토큰 한국어 대화에서는 읽는 AI가 프로젝트 목표와 금지 라이브러리까지 놓쳤습니다.
- 크기를 바꿔 보면 모든 지점에서 coverage가 v1.2.1보다 토큰을 적게 쓰고 더 많이 맞혔습니다. 예를 들어 coverage는 원문의 10% 크기로 90%를 맞혔습니다. v1.2.1은 16% 크기로 69%, 28% 크기로 90%였습니다. 또 v1.2.1은 예산을 3%로 줘도 문서가 6천–9천 토큰 밑으로 줄지 않았습니다.

v1.2.1이 진 원인은 여섯 가지였습니다.

1. **선택에 쓰는 몫이 작았습니다.** 문장을 고르는 알고리즘은 coverage와 같은데, "중요한 맥락"에 돌아가는 분량이 문서의 6–28%뿐이었습니다. 나머지는 최근 원문(25%), 요청 목록, 결정 목록, 코드·파일 목록, 메시지 참조 색인(7–12%)이 차지했습니다.
2. **한국어 가짜 결정이 생겼습니다.** "지시 + 변경 표현"을 결정으로 봤는데, "표 머리글 좀 바꿔 주세요" 같은 수정 요청이 모두 여기에 걸렸습니다. 뒤에 나온 비슷한 요청은 그 결정을 "변경했다"고 연결했습니다. 결정 목록에는 몫 제한도 없었습니다. 이 때문에 한국어 정답률(72%)이 영어(85%)보다 낮았습니다.
3. **예산을 넘겼습니다.** 문서가 예산보다 9–28% 컸습니다.
4. **참조 복원이 비용을 잘못 셌습니다.** "이 방식은 …" 문장은 앞 문장과 묶여 두 문장 값을 비용으로 냅니다. 그런데 앞 문장이 먼저 따로 뽑힌 뒤에도 묶음의 비용이 그대로 남았습니다. 그래서 정보가 담긴 문장이 계속 밀렸습니다. 앞 문장을 가리키는 질문의 정답률은 10%였습니다.
5. **거절을 알아보지 못했습니다.** "아니요, Redis 캐시는 쓰지 않기로 해요"는 결정으로도 금지로도 잡히지 않았습니다. 그래서 문서에 "Redis 도입 제안"만 남을 수 있었습니다.
6. **마지막 답변의 핵심 문장 6개가 바로 아래 최근 원문과 겹쳤습니다.**

### v1.3에서 바꾼 것

- **분량 배분** (`DEFAULT_LAYOUT`):
  - 최근 원문은 6%(최소 400토큰)로 줄였습니다. 마지막 두 메시지는 v1.2와 같이 각 2,500토큰까지 넣고, 그 앞 메시지는 예산의 6%(최대 1,500토큰)까지 넣습니다. 잘린 가운데는 계속 선택 후보가 됩니다. 마지막 두 메시지의 상한도 예산에 비례해 줄여 봤지만, 실제 대화에서 최근 대화 보존이 10점 떨어져 되돌렸습니다(아래 "실제 대화로 확인").
  - 코드는 6%(최소 300), 목록 섹션은 기존 몫의 0.4배로 줄였습니다.
  - 결정·지시는 합쳐서 20%까지입니다. 결정은 그 절반까지 쓰고, 나머지는 금지·제약사항에 남겨 둡니다.
  - 참조 색인은 기본으로 끕니다.
  - 남은 분량은 모두 coverage 선택에 갑니다. 이전 배분은 `V12_LAYOUT`으로 남겨 비교에 씁니다.
- **예산 맞추기**: 첫 계산이 예산을 넘거나 4% 넘게 모자라면, 최대 두 번까지 차이를 "중요한 맥락"에서 빼거나 더합니다(허용 오차 +2%). 이제 예산이 작아지면 문서도 작아집니다.
- **비용 다시 계산**: `greedyCoverage`가 고를 때마다 비용을 다시 읽습니다(`CoverHooks.cost`). 앞 문장이 이미 들어간 묶음은 그만큼 싸집니다.
- **결정·금지 규칙**:
  - 수정 요청은 "A 말고 B", "대신", "instead of"처럼 이전 선택을 뒤집는 표현(`REVERSAL_RE`)이 있을 때만 결정이 됩니다.
  - "~로 가죠/하죠", "~하기로 해요"는 결정입니다.
  - "~는 쓰지 않기로", "won't use", "decided against"는 금지가 되어 제약 섹션에 갑니다.
  - 분류 규칙이 바뀌었으므로 `CACHE_VERSION`을 5로 올렸습니다.
- **중복 줄이기**: 명령어 목록에 모두 있는 셸 코드 블록은 다시 넣지 않습니다. 마지막 답변이 최근 원문에 잘리지 않고 다 보이면, 핵심 문장은 2개만 넣습니다.
- **조정하다 되돌린 것**:
  - 파일 목록을 작은 예산에서 10개로 줄였더니, 질의응답 지표는 약간 올랐지만(+1.2점) 기존 지표의 개체(경로·명령) 보존이 9점, 사용자 단어가 4점 떨어졌습니다. 코딩 대화를 넘겨받을 때 파일 목록이 쓸모 있어서, 예산 200토큰당 1개(최대 40개)로 되돌렸습니다.
  - 관련도 가중치(`relPrior`)를 없애면 오히려 나빠져서 0.5로 유지했습니다.

1·2차 실험의 지표(합성 대화 4개, 기본 예산)로도 비교했습니다. 종합 점수는 v1.3 86.7, v1.2 배분 84.6, coverage 85.4입니다. 사실 보존은 v1.3 81.7%, v1.2 배분 65.0%입니다. 반면 사용자 단어(83.9% 대 89.3%)와 개체(73.7% 대 83.8%)는 v1.2 배분이 더 높습니다. 요청 목록과 최근 원문을 줄인 대가입니다.

### 실제 확장으로 다시 잰 보존율 (v1.3.3)

실제 계정에서 확장을 직접 돌려, 인수인계본을 같은 대화의 전체 추출본(JSON)과 비교했습니다([테스트 보고서 §6.6](test-report.md), `npm run check:real`). 압축된 대화만 보면 ChatGPT 6개는 종합 63.5(핵심어 89%, 사용자 단어 80%, 사실 문장 38%)였고, 같은 예산의 단순 커버리지는 68.3이었습니다. Claude 4개는 종합 86.7(사용자 단어 99%, 사실 문장 86%)이었고, 커버리지는 77.4였습니다. 발췌 578개는 모두 인용한 메시지에 원문 그대로 있었습니다.

### 실제 대화로 확인

질의응답 평가는 합성 대화로만 했습니다. 그래서 2차 실험과 같은 방식으로 사용자의 실제 대화를 다시 받아 1·2차 지표로 확인했습니다. ChatGPT 32개와 Claude.ai 3개를 받았고, 그중 1.2만 토큰 이상인 **31개**(약 152만 토큰)를 썼습니다. 파일은 실험 직후 지웠고, 아래 수치만 남겼습니다.

| 기본 예산 | v1.2.1 | **v1.3** | coverage | skeletonCoverage |
|---|---|---|---|---|
| 종합 | 60.1 | **60.9** | 62.5 | 62.5 |
| 사실 보존 | 29.7% | **33.2%** | 39.6% | 37.3% |
| 핵심어 / 개체 | 87.1% / 44.5% | 88.9% / 43.9% | 96.2% / 43.0% | 95.1% / 44.0% |
| 사용자 단어 | 80.0% | 79.4% | 66.5% | 66.4% |
| 최근 | 67.2% | 62.6% | 68.2% | 76.9% |
| 앞 문장 잃음 (dangl) | 30.3% | **24.0%** | 56.8% | 36.7% |
| 평균 출력 | 10,377토큰 | **9,653토큰** | 8,610토큰 | 8,643토큰 |

- **개선 폭은 합성 대화보다 작습니다.** 실제 대화는 메시지 수가 적고(대부분 10개 안팎) 메시지 하나가 매우 깁니다. 그래서 v1.2.1에서도 요청 목록, 결정 목록 같은 구조 섹션이 예산을 덜 먹었습니다. 합성 대화의 "긴 답변형"에서 v1.2.1이 이미 98%였던 것과 같은 이유입니다.
- **최근 대화 보존과 사실 보존은 서로 맞바꾸는 관계였습니다.**
  - 마지막 두 메시지의 상한을 예산의 10%로 줄인 첫 설정은 종합 62.2, 사실 38.1%를 냈습니다. 대신 최근 대화 보존이 57.4%(−10점)로 떨어졌습니다.
  - 마지막 답변에는 대개 작업 중인 코드나 결과가 있어서 다음 AI가 이어서 일하려면 꼭 필요합니다. 그래서 상한을 v1.2의 2,500토큰으로 되돌렸습니다.
  - 그 결과 최근 대화 보존은 62.6%가 됐고, 사실 보존은 33.2%(v1.2.1보다 +3.5)로 덜 올랐습니다.
  - 이 되돌림은 합성 대화 문서를 하나도 바꾸지 않았습니다(질의응답 결과 그대로).
- 원문의 10% 예산에서는 v1.3의 종합 점수가 v1.2.1보다 낮습니다(45.4 대 49.0). 다만 출력도 20% 짧습니다(6,359 대 7,937토큰). v1.2.1은 예산보다 큰 문서를 냈기 때문입니다. 원문의 30% 예산에서는 v1.3이 높습니다(64.8 대 63.9).

### 한계

- **합성 대화입니다.** 채우는 문장이 템플릿에서 나와서, 심어 둔 사실의 드문 단어가 눈에 잘 띕니다. 그래서 개념 커버리지에 유리합니다. 실제 대화로 같은 질의응답 평가를 하려면 질문을 만들 때 대화 내용을 AI에게 보여 줘야 해서 하지 않았습니다.
- **질문은 사실 확인입니다.** 다음 AI가 작업을 실제로 이어 가는 능력(코드 수정, 판단)은 재지 않았습니다.
- **읽는 AI는 Haiku 하나입니다.**

## 방법

### 데이터와 개인정보

- 사용자의 로그인된 Chrome에서 최근 대화 목록을 읽기 전용으로 가져왔습니다. 확장이 쓰는 것과 같은 요청입니다(ChatGPT `/backend-api/conversation/{id}`, Claude `chat_conversations/{id}`). 그중 본문이 2만 자(약 1.2만 토큰) 이상인 대화만 썼습니다. 다운로드마다 파일 이름·출처·크기를 알리고 사용자 허락을 받았습니다.
- 대화는 현재 분기만 남기고, 사고 과정·숨은 도구 출력·검색 결과 본문을 뺀 형태로 한 파일에 담았습니다. 이 파일은 저장소 밖 임시 폴더에서 로컬로만 처리했고, 실험 직후 삭제했습니다.
- 이 문서와 저장소에는 **집계 수치만** 있습니다. 대화 내용, 제목, ID는 남기지 않았습니다.

### 공정한 비교

1. 대화마다 모든 알고리즘에 같은 토큰 예산을 줍니다. 엔진은 고정 부분(안내문, 마지막 두 메시지) 때문에 아주 작은 예산을 넘을 수 있어서, 표의 "평균 토큰" 열을 함께 봐야 합니다.
2. 예산은 원문의 5%·10%·20%·30%·50%와 **기본값**(엔진 기본 예산: 원문의 12%, 8k–32k)입니다. 실제 제품이 쓰는 것은 기본값입니다.
3. Lucian 외의 알고리즘은 같은 형식(메시지별 `### [#mN] User/AI` + 원문 단위)으로 출력합니다.

### 지표 (모델 없이 계산, 높을수록 좋음)

| 지표 | 뜻 |
|---|---|
| 사실 보존 (fact) | 대화 전체에서 고르게 뽑은 사실 문장 40개 중, 출력의 한 줄이 그 문장의 내용어 60% 이상을 담고 있는 비율 |
| 핵심어 (terms) | 대화의 TF-IDF 상위 300개 단어의 가중 재현율 |
| 사용자 (user) | 사용자가 쓴 단어(요청, 제약, 결정)의 가중 재현율 |
| 개체 (ents) | URL, 파일 경로, 식별자, 단위가 붙은 숫자, 버전의 재현율 |
| 최근 (recent) | 마지막 메시지 4개의 단어 재현율 (현재 상태) |
| 중복 (dup, 낮을수록 좋음) | 출력에서 같은 줄이 반복된 비율 |
| 앞 문장 잃음 (dangl, 낮을수록 좋음, 2차 실험) | "이…", "그래서…", "This…"처럼 앞 문장을 가리키며 시작하는 남긴 문장 중, 그 앞 문장이 출력에 없는 비율 |
| **종합** | 0.3 사실 + 0.25 핵심어 + 0.2 사용자 + 0.15 개체 + 0.1 최근 |

이 지표는 단어·개체·문장의 **보존**을 잽니다. 바꿔 말한 의미나 문서 구조(결정·제약·할 일 섹션)가 다음 AI에게 얼마나 쓸모 있는지는 재지 못합니다. 그래서 수치와 함께 출력 몇 개를 직접 읽어 확인했습니다.

### 알고리즘

| 이름 | 방법 |
|---|---|
| `recent` | 마지막 메시지부터 예산이 찰 때까지 그대로 (대화 끝부분 복사와 같음) |
| `headTail` | 첫 요청 + 최근 메시지 |
| `lead` | 모든 메시지의 앞 k개 단위 (k는 예산에 맞춰 최대로) |
| `tfidf` | 단위별 TF-IDF 점수(길이 정규화, 최근성·사용자 가중) 순 |
| `textrank` | LexRank: 드문 단어를 공유하는 단위끼리 이은 그래프의 PageRank |
| `mmr` | 사용자 요청과의 관련도 − 이미 고른 것과의 유사도 (Carbonell & Goldstein 1998) |
| `coverage` | 예산 제약 최대 커버리지: 단어·단어쌍 개념의 가중치 합을 토큰당 가장 많이 새로 덮는 단위부터 (Khuller 1999, Gillick & Favre 2009, lazy greedy) |
| `skeletonCoverage` | 최근 원문(예산 25%) + 사용자 요청(누적 42%까지)을 먼저 넣고, 남은 예산을 `coverage`로 |
| `coverage+compact` | `coverage` 출력에서 군더더기 단어(그리고, 사실, basically…)를 지우고 남은 토큰으로 다시 채움 |
| `dedupe+…` | 아래 무손실·준무손실 축약을 먼저 한 뒤 같은 알고리즘 |
| `lucian` | 현재 엔진 (기본값) |
| `lucian/v1.1` | v1.1 엔진 설정 (관련도 순 과거 맥락, 긴 원문, 코드 25%) |
| `lucian/…` | 엔진의 예산 배치·선택 방식을 하나씩 바꾼 변형 (`algorithms.ts` 주석 참고) |

### 무손실·준무손실 축약

선택 전에 정보를 잃지 않고 줄일 수 있는 양도 쟀습니다.

- **정확한 중복**: 정규화한 텍스트(30자 이상)가 뒤에 다시 나오는 단위. 가장 최근 것만 남깁니다.
- **이전 버전 코드**: 같은 언어의 뒤 코드 블록이 줄의 60% 이상을 공유하면 앞 블록은 이전 버전입니다. 최종 상태는 남고 수정 이력만 빠집니다.
- **거의 같은 문장**: 내용어의 80% 이상을 비슷한 크기의 뒤 단위와 공유하는 문장.
